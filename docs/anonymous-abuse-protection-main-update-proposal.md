## 提案するPR本文

### Problem

Static widgets call the hub directly from visitors' browsers. Keep that deployment
model and the existing CORS allowlist, but enforce resource limits for every
anonymous request, including requests made by scripts outside a browser.

Current main includes `FreeModelThrottle`, but anonymous buckets prefer the
caller-supplied Origin header. A direct client can rotate Origin values to obtain
new buckets. Legitimate visitors from one embedding origin also share a bucket.
Production uses `:memory_store`, so limits are independent per Puma process.
The direct MCP proxy has no equivalent admission gate, and anonymous `/chats`
can invoke inference without passing through `FreeModelThrottle`.

CORS, DNS reverse lookups, Origin, Referer, User-Agent and client-provided session
identifiers must not serve as authentication or authoritative quota identities.
The objective is to bound anonymous consumption, not to identify browser clients
or prove that a caller visited an approved website.

### Proposed behavior

1. Add a shared, atomic admission policy backed by PostgreSQL (already required
   by the app), with limits spanning all Puma workers and instances sharing the
   database. Do not silently fall back to unlimited access if storage fails.
2. For anonymous requests, key per-client limits by the validated network client
   IP, HMAC-hashed with the server secret. Ignore Origin when assigning quota.
   Configure only the actual trusted ingress proxies; overwrite untrusted
   forwarding headers and prevent public access that bypasses the ingress.
   The same IP retains the same budget with missing or changing Origin headers.
3. Apply admission to `/api/.../single_llm_calls` and
   `/api/mcp_tools/:tool_id/call` before provider execution. Match every concrete
   route generated by routes.rb, including optional nested route variants.
   Distinguish LLM and MCP rates and concurrency; cap each MCP tool globally.
4. Close alternate anonymous inference paths. For the initial scope, return 403
   for anonymous `/chats` and `/chat_streams`, directing clients to
   `single_llm_calls`. Document this compatibility change. If maintainers need
   anonymous legacy clients, implement the same admission policy and per-tool
   policy inside the server orchestration loop before retaining those paths.
   Cover tool-discovery refreshes that make outbound MCP calls with a separate
   discovery limit or serve cached metadata; the execution limits alone do not
   protect this outbound path.
5. Resolve identity explicitly: a supplied invalid/malformed Authorization header
   returns 401 and must not downgrade to anonymous. Apply anonymous model
   allowlists, and retain active/public_to_anonymous MCP visibility checks. A
   forged nonempty bearer must not bypass anonymous controls.
6. Bound request body before JSON parsing, message count/bytes, schema size,
   argument size, provider output tokens/context, execution time and MCP result
   bytes. Validate merged model defaults and caller overrides. Normalize each
   provider's token parameters (including Ollama options); reject unknown or
   unbounded settings. Preserve current provider timeout and disconnect handling.
7. Add global daily consumption reservations and emergency switches for LLM and
   MCP. Per-IP limits alone do not stop a distributed attack. Reserve capacity
   atomically before execution, settle usage afterward and recover expired
   reservations without releasing capacity for work that is still running.
   For local inference use bounded concurrency, elapsed time and token limits;
   for house-funded providers add conservative input/output token reservations
   and a provider-aware budget. Do not describe elapsed time as a monetary cap.
8. Keep signed-in callers' own-key behavior; apply a shared authenticated budget
   for signed-in users spending the house credential as well. Unify or explicitly
   separate this behavior with FreeModelThrottle so two inconsistent anonymous
   counters do not run. Own-key requests still retain ordinary API/body safeguards.

### API responses and lifecycle

- Before SSE begins: HTTP 400 for invalid settings, 413 for oversized bodies,
  429 for rate/IP quota exhaustion, 503 for shared capacity, disabled service or
  unavailable admission storage. Use stable machine-readable error codes and
  Retry-After for retryable rejections. Never start paid work before admission.
- After SSE begins: emit a structured `error` event and close; do not emit a
  successful `done`. A begun SSE response cannot change to HTTP 429/503 later.
- MCP deadline: 504; oversized upstream result: bounded failure (502).
- Release concurrency reservations on success, provider errors and verified
  cancellation. A proxy disconnect or timeout is not proof that GPU/provider
  work stopped; keep a bounded lease until termination is confirmed or an
  enforced provider deadline expires. Bound upstream reads while streaming;
  checking size after buffering the full response is insufficient.
- Expose Retry-After via CORS. The widget should show the error and stop its
  orchestration loop; automatic retry must not create another load loop.

### Suggested initial configuration (deployment-tuned examples)

| Setting | Example | Purpose |
| --- | --- | --- |
| ANONYMOUS_MODELS | operator-selected tool-capable model slugs | Explicit anonymous model set |
| ANONYMOUS_LLM_RATE | 30 per IP / 60 seconds | Count all LLM turns, not user questions |
| ANONYMOUS_MCP_RATE | 60 per IP / 60 seconds | Bound direct tool execution |
| ANONYMOUS_LLM_PER_IP / GLOBAL | 1 / 2 | Bound occupied inference slots |
| ANONYMOUS_MCP_PER_IP / GLOBAL | 2 / 8 | Bound outbound tool slots |
| ANONYMOUS_BODY_BYTES | 1048576 | Account for guide + tool-result history |
| ANONYMOUS_OUTPUT_TOKENS | 4096 | Provider-enforced output cap |
| ANONYMOUS_LLM_SECONDS / MCP_SECONDS | 180 / 30 | Provider-enforced deadlines |
| ANONYMOUS_DAILY_* | deployment-defined | Required global time/token/cost budget |

These values are proposed starting points, not measured safe production limits.
Test realistic TogoMCP guide/schema/result sizes before enforcing body/context
limits. The widget permits max-rounds=10 and max-exchanges=4: one conversation
can issue up to 40 LLM requests, plus tools. Do not interpret four exchanges as
four server requests. A six-requests/minute policy from the earlier proposal can
interrupt a fast ten-round question. An older slow local model may instead need
a longer bounded deadline, decided by measured latency and available capacity.
Shared-NAT users share the IP budget; return an understandable retry message.

### Acceptance checks

- Without Origin, with a forged allowed Origin and with rotating arbitrary
  Origins, the same client IP exhausts the same quota.
- Two different client IPs under the same allowed Origin have independent IP
  quotas and share global capacity/budget.
- Untrusted X-Forwarded-For/X-Real-IP cannot create new quota identities;
  explicitly trusted ingress resolves the intended client IP.
- Invalid bearer values fail authentication and cannot bypass admission.
- Concurrent requests from two real worker processes cannot exceed shared limits.
  Include database-unavailable, admission race and bounded cleanup scenarios.
- Direct MCP calls and anonymous legacy endpoints cannot bypass the policy;
  repeated metadata refresh cannot create unbounded outbound MCP traffic.
- No model/tool/provider operation starts after rejected admission. Own-key and
  authenticated house-key behavior are covered separately.
- Provider output settings, oversized/chunked bodies, excessive history/schema,
  large upstream results and stalled providers produce bounded failures.
- Disconnect, timeout and emergency stop do not release a slot prematurely while
  upstream work remains active; recover bounded leases after worker failure.
- A normal anonymous `single_llm_calls -> tool_call -> MCP result -> next LLM
  turn -> answer` completes with up to ten LLM turns and existing static HTML.
- HTTP pre-stream and SSE mid-stream errors both stop the widget without retries.
- Rotating IPs still cannot exceed the global budget; no counter/backend failure
  falls back to unlimited house-key use.

### Deployment and limits

Apply the migration, configure allowlists/limits and trusted ingress, then roll
out all workers consistently with admission disabled or anonymous traffic
briefly paused during the mixed-version interval. An old worker must not remain
as an unprotected route. Put request-size, connection/time and coarse rate limits
at ingress too; application-level policy cannot stop bandwidth exhaustion.

Do not embed shared secrets in HTML, add a Google-login requirement or add a
new widget proxy. The static hosting configuration remains intact. No assertion
is made that allowed-origin browsers are authenticated, or that distributed
abuse can be perfectly attributed to individual people.

## 最新main調査の根拠

- app/services/free_model_throttle.rb: bucket_forはuser優先、匿名はOrigin優先。
  ファイル自体がプロセス単位のmemory_store制限であることを明記。
- config/environments/production.rb: config.cache_store = :memory_store。
- single_llm_calls_controller.rb: FreeModelThrottle.check!はsink.phaseとheartbeat開始後。
- mcp_tool_calls_controller.rb: 可視性検査後に直接McpClientを実行し、入場制限なし。
- chats_controller.rb: 匿名のLlmRbFacade.call!にFreeModelThrottle呼び出しなし。
- mcp_tools_controller.rb#index: メタデータ取得時にfetcher.fetch!で外部アクセス。
- cors.rb: Originの許可リストはすでに環境変数化済み。CORS自体の再実装は不要。
